## 1. Executive Summary

### 1.1 问题与目标

部门成员已有零散的质量与效率改进行动，但对 QCC 方法不熟悉，缺少把工作事实组织为规范过程和成果的支持；整理 PPT、准备评审的额外工作也使成员抵触参与。

qcc-copilot 帮助成员从真实工作出发，发现、提炼并推进 QCC 课题，形成有明确收益、可推广复用、方法应用准确的成果，再从中孵化优秀项目参与评奖。

### 1.2 已确认的产品决策

| 编号 | 已确认事项 | 产品含义 |
|---|---|---|
| C01 | 目标是部门可分发工具 | 设计可复用产品，不在本次需求阶段替负责人执行个人 QCC 课题 |
| C02 | 以日常改进带动 QCC | 从工作问题和已有行动切入，将方法学习融入改进过程 |
| C03 | 支持存量梳理与后续引导 | 已做过、正在做和待开展的改进均可进入，支持继续迭代 |
| C04 | 成员主要使用编程 Agent | 以可安装的 QCC Skill 为主要入口，复用成员现有工作环境 |
| C05 | 成员侧 Skill + 负责人轻量汇总 | 成员独立推进，负责人了解候选课题、进展、价值、缺口和参评准备情况 |
| C06 | 同时支持两种选题入口 | 既评估、提炼成员提供的改进，也从指定资料中发现候选课题 |
| C07 | 默认按需启动 | 成员指定项目或资料，启动后 AI 主动整理、挖掘和引导，并可续接 |
| C08 | 三项核心评奖视角 | 明确收益、成果可推广性、QCC 方法与材料逻辑完整性；权重未定 |
| C09 | 成果推广性首先从选题判断 | 判断共性痛点、价值和受益范围，再验证方案的可复制性与实际采用情况 |
| C10 | 易用性与成果推广性分别评价 | 成员使用工具的投入不作为课题能否跨部门推广的替代指标；未约定每周时间预算 |

### 1.3 方案概述

成员在现有 Agent 中调用 Skill，提供改进描述或指定资料。工具围绕“课题发现与提炼 → 价值和推广潜力评估 → QCC 方法引导 → 证据与收益 → 成果生成与自检”提供持续支持，并输出可供负责人汇总的结构化摘要。

AI 尽量承担资料整理、计算调用、制图、起草和检查；成员补充或确认真实工作事实，完成实际改进行动。工具支持指出证据不足和验证任务，不把未知内容转成已发生事实。

### 1.4 成功指标

以下为建议测量口径，不是已取得的结果。试点人数、观察周期及业务目标值均为 TBD，由试点方案确定。

| 指标 | 测量口径 | 目标状态 |
|---|---|---|
| 候选课题有效率 | 负责人评为值得开展或继续打磨的候选数 / 已审阅候选数；保留不采纳原因 | 阈值 TBD |
| 正式成果核心主张可追溯率 | 有可定位证据及相应核验记录的核心收益、效果和推广主张数 / 正式成果全部此类主张数 | 建议正式成果完整追溯；不以有链接替代证据有效性判断 |
| 材料准备人工投入变化 | 同等材料范围与质量要求下，使用前后整理、制图、排版及校对的人工耗时差异 | 基线与目标 TBD；仅衡量工具使用效果 |
| 方法与论证检查通过情况 | 按适用规则检查的方法错误、事实冲突、证据缺口及其修复情况，分别统计严重度 | 建议正式成果无未解决的严重错误 |
| 跨团队复用验证情况 | 记录适用团队、实际复现或采用记录、接入成本和收益反馈；潜在覆盖与已采用分开统计 | 试点目标 TBD；衡量 QCC 成果推广性 |

## 2. User Experience & Functionality

### 2.1 用户角色

| 角色 | 诉求 | 典型行为 |
|---|---|---|
| 改进发起人 / 课题成员 | 将自己的工作改进落实为 QCC，减少方法理解和材料整理负担 | 描述问题、指定资料、确认事实、执行改进、审阅成果 |
| 部门 QCC 负责人 | 发现值得培养的课题，辅导关键缺口，筛选参评成果，推动复用 | 查看汇总、给出反馈、调整辅导重点、判断参评准备情况 |
| 潜在复用团队 | 判断成果能否解决自己的问题，以及如何采用 | 阅读复用说明、核对条件、复现做法并反馈效果 |

评审者是成果的读者；MVP 不要求其注册或使用另一套系统。

### 2.2 成员旅程

1. **按需启动**：提供一个改进描述，或指定仓库、Issue、复盘、数据等资料范围。
2. **理解当前工作**：AI 汇总问题、行动、已有证据及当前阶段，列出读取范围与未覆盖内容。
3. **发现与提炼课题**：输出候选课题、依据、价值假设、共性场景与疑点；支持聚焦、拆分、合并，成员选择推进对象。
4. **按当前阶段进入**：识别可沿用的工作记录、缺失的必要环节及下一步验证任务，不要求重做已经有依据的工作。
5. **持续更新**：成员带入新增记录或数据，AI 更新课题档案、证据、收益测算与下一步建议；换会话后可恢复。
6. **形成成果**：汇总收益、方法论证与复用做法，生成报告、图表和 PPT，开展评审自检与修改。
7. **发布摘要**：成员按需导出课题摘要，负责人汇总、辅导和筛选；反馈可带回课题继续处理。

### 2.3 用户故事与验收条件

以下验收条件是 PRD 设计建议；各项均属于完整 MVP 能力链的一部分。

#### US01：提炼我已有的改进

作为成员，我希望提供已做或正在做的改进，让 AI 帮助识别合适的 QCC 课题，以便利用已有工作积累。

- 能接收自然语言及可访问的相关资料，输出当前问题、改进行动、预期或已知收益、证据和未知项。
- 课题建议围绕问题、目标与受益对象展开，允许建议聚焦、拆题或合题。
- 区分“功能已实现”“已经证明有收益”“已经被其他团队采用”。
- 不将代码或提交数量直接折算为节省人天，也不把材料补写描述成当时已执行的活动。

#### US02：从我的工作资料中发现候选课题

作为成员，我希望 AI 分析我指定的资料并提出候选课题，以便发现有价值的改进机会。

- 每个候选项包含问题、来源依据、潜在受益对象、收益假设、推广条件及待验证项。
- 对相关来源做聚合与去重；有依据时解释候选项之间的重叠、拆分或合并关系。
- 说明扫描范围和未覆盖部分；资料不足时报告不足，不强行凑出固定数量的候选题。
- 候选发现可在按需调用内主动完成，不要求后台常驻或持续监控日常开发。

#### US03：在实际改进中应用 QCC 方法

作为成员，我希望用工作语言获得下一步建议，以便在推进事情的同时准确应用 QCC。

- 为选中的课题关联适用方法规则，记录当前阶段、已具备材料、必要缺口与下一步。
- 建议同时说明要回答的问题、推荐方法、适用理由、所需输入及预期产物。
- 原因假设、要因验证、对策、实施记录和效果验证可建立明确关联；相关性或评分本身不替代因果验证。
- 允许回到前序阶段、修正课题范围和标注不适用项；不能仅以页面齐全判断过程完成。
- 缺数据时形成可执行的补充或验证建议，并允许继续整理草稿。

#### US04：说明实际价值并核算收益

作为成员，我希望收益有清晰口径和可复算依据，以便回答“究竟节省了多少人力”。

- 记录基线、改善后值、统计周期、样本或事件数量、计量单位和数据来源。
- 区分实测、用户提供、估算及预测；实测结果与外推场景分别展示。
- 明确建设、运行和维护等人工成本的计入方式，支持净收益为零或负值。
- 计算走确定性脚本，输出公式、输入、单位、结果和假设；人工操作时间与系统等待时间分开。
- 无必要输入时输出缺口和可填写模型，不生成无依据的收益数字。

#### US05：让其他部门能够复用成果

作为成员，我希望提炼通用做法和采用条件，以便其他团队判断是否适用并完成复用。

- 评估共性痛点、目标团队、必要依赖、接入与维护成本、边界和预期收益。
- 输出复用说明：适用条件、所需资产、操作步骤、验证方法及维护责任建议。
- 区分潜在适用、已完成复现验证和已有采用记录，推广数量必须对应具体证据。
- 对依赖个人资源、特殊权限、专用环境等限制给出说明和改进建议。
- 不以“容易安装”或“成员整理材料耗时少”作为课题本身可推广的证明。

#### US06：积累证据并跨会话继续

作为成员，我希望课题状态和证据落在持久文件中，以便持续更新并追溯每个结论。

- 保存课题标识、版本、来源、阶段状态、事实、假设、证据引用、计算结果和待办。
- 核心数字和结论能够定位到文件、数据位置、记录或链接，并记录可用的来源版本信息。
- 发现来源或计算输入变化时，标记受影响结论及材料需要重新核验，不继续展示为当前已确认成果。
- 新会话读取档案后能恢复当前状态与下一步；已有人工修订可保留并处理冲突。

#### US07：生成可用于评审准备的成果材料

作为成员，我希望从同一份课题档案生成材料，以便减少重复整理并保持口径一致。

- 生成课题报告、收益说明、图表及对应数据、推广复用说明、PPT 和评审问题清单。
- MVP 的 PPT 验收包含可打开检查的文件，不能仅以大纲或逐页文案代替；格式、企业模板和可编辑范围见 D04。
- 报告与 PPT 的数字、单位、周期和结论与当前档案一致；每项核心主张有引用或明确的缺口标记。
- 支持草稿与参评准备材料的不同状态；缺证据内容不得作为已证实事实进入正式结论。
- 能检查内容覆盖、文本溢出、占位符和渲染情况；无法验证的项目明确列出，不声明已检查通过。

#### US08：获得可操作的评审反馈

作为成员，我希望按三项评奖视角检查成果，以便优先修复影响最大的缺口。

- 对价值、推广、QCC 方法及 PPT 论证分别输出“依据 / 发现 / 影响 / 建议 / 待补证”。
- 检查方法是否适用、数据是否可比、原因与对策是否对应、收益是否重复计入、推广主张是否有依据。
- 没有具体评分细则时输出定性检查及其依据，不生成虚构的官方评分、权重或获奖概率。
- 自检与生成分为独立步骤；不要求必须使用多个模型，模型自检也不等同外部评审通过。

#### US09：负责人轻量汇总与辅导

作为负责人，我希望查看统一口径的课题摘要，以便发现辅导机会和参评候选。

- 成员可按需导出摘要，包含课题标识、负责人、问题、收益口径、推广情况、当前阶段、关键缺口、下一步及更新时间。
- 负责人可汇总多份摘要，按阶段、三项评奖视角和待辅导事项查看，并保留成员原始说明。
- 同一课题的新版本可更新原记录；保留版本信息，标明陈旧、缺失或冲突的摘要。
- 支持带课题标识的反馈回流；轻量汇总不依赖负责人取得全部源代码、日志和原始数据。
- 最小落地建议为“标准摘要包导出 / 导入 + 汇总表”；实际载体与更新机制由 D05 决定。

#### US10：安装、使用与分发

作为成员，我希望在已有 Agent 中使用一致的能力，以便不必另外掌握复杂系统。

- 分发包包含 Skill 指令、规则参考、脚本、模板、安装和使用说明，并标识版本及运行依赖。
- 验证目标宿主中的安装、两种入口、续接、计算、材料导出和摘要汇总完整链路。
- 首批宿主及操作系统由 D01 决定；有明确的兼容矩阵和实测结果，不笼统声明所有 Agent 均已支持。
- 模型由宿主提供，额外工具与模型能力不足时说明受影响步骤和可继续进行的工作。

### 2.4 MVP 交付物

| 交付物 | 作用 | 最低要求 |
|---|---|---|
| 可分发 Skill 包 | 面向成员和负责人提供入口 | 能在选定宿主完成 US01–US10 的对应工作流 |
| 候选课题清单 | 支撑两种入口的选题决策 | 有来源、价值与共性分析、假设、待验证项 |
| 持续课题档案 | 跨会话维护方法、事实和证据 | 机器可读且可人工检查，有版本和下一步 |
| 价值与推广材料 | 证明收益并支持其他团队采用 | 收益计算底稿、适用条件、复用说明及验证记录 |
| 成果材料包 | 支持汇报和参评准备 | 报告、图表与底稿、PPT、方法检查和评审问题清单 |
| 课题摘要与汇总结果 | 支持负责人辅导和筛选 | 可导出、合并、更新、识别缺口，并可回传反馈 |

MVP 应交付上述完整的最小闭环。允许缩减初期支持的宿主、连接器和模板数量，但两种入口、价值核算、推广评估、QCC 引导、成果材料与轻量汇总均需保留。

### 2.5 非目标与边界

- 首期不建设统一账户、审批流、项目管理和全部原始资料集中存储的大型平台。
- 默认不伴随日常开发持续监听、自动提醒；按需启动后仍需主动发现和处理资料。
- 不要求先培训完完整方法论再使用，也不要求每个小改进都形成参评项目。
- 工具支持真实改进的设计和验证；MVP 不以接管开发实施、修改业务仓库或操作生产环境作为必要能力。
- 不承诺获奖，不把 AI 自检视作官方评分或真实收益的替代证明。
- 通用 RAG、视觉质检、完整 QMS 和无关质量工程工具不纳入首期。

## 3. AI System Requirements

### 3.1 AI 与工具职责

| 能力 | AI 的职责 | 所需工具能力 |
|---|---|---|
| 资料理解与候选发现 | 聚合工作问题、解释依据、形成候选及疑点 | 有界文件读取与搜索；Git 历史；选定连接器 |
| 方法引导 | 选择适用方法、解释下一步、检查阶段间关系 | 版本化方法规则、契约校验、课题状态读写 |
| 价值与效果分析 | 建议统计口径、解释结果与局限 | 确定性计算、单位校验、必要统计检验和图表生成 |
| 推广评估 | 分析共性、约束、复用方案及验证缺口 | 复用模板、证据引用、采用记录 |
| 成果编译 | 组织内容、起草、检查材料间一致性 | 文档与 PPT 生成、图表导出、渲染和版式检查 |
| 负责人汇总 | 汇总课题信息、发现辅导重点 | 摘要校验、版本合并、表格或报告导出 |

宿主负责模型与通用工具能力；Skill 提供领域规则、可执行脚本和模板。具体实现语言、生成库及远端 API 均为 TBD。

### 3.2 方法规则与事实要求

- 以“价值 / 推广 / QCC 遵循”三维要求为初始规则框架；细则的来源、版本与适用范围可追溯。
- 依据课题类型和实际评奖要求选用流程，不把调研中的十一阶段或某个项目的强制页面链视作所有场景的统一标准。
- 鱼骨图分类、柏拉图阈值、统计方法等需要说明适用条件；可识别的图形不等于方法应用正确。
- 资料中的事实、成员陈述、AI 推断、估算和示例分别标记；有来源不代表来源足以支持当前主张。
- 核心结论必须关联支持它的证据与核验记录，不能用 AI 的置信描述代替。
- 草稿可保留缺口；“结构完整”“证据充分”“参评准备状态”分别判断。

### 3.3 评估策略

采用固定输入样例、确定性脚本检查、真实宿主端到端验证和负责人审阅相结合的方式。以下是建议最小验收情境，不代表已经执行或通过。

| 编号 | 情境 | 验收重点 |
|---|---|---|
| E01 | 成员提供已有改进及部分记录 | 能提炼课题，区分实施事实、效果证据与缺口 |
| E02 | 指定资料包含多个改进及重复叙述 | 有依据地发现候选，去重并建议聚焦，无凭空凑题 |
| E03 | 文件读取不完整或远端不可访问 | 报告覆盖范围与未读内容，不将未读内容当作无问题 |
| E04 | 收益模型缺少基线、混淆单位或只有系统等待时间 | 标明缺口；不输出无依据的人天收益 |
| E05 | 已知输入可复算，含建设维护成本和负收益 | 计算、单位、成本处理与预先核定的参考结果一致 |
| E06 | 原因有相关性但缺验证，对策与原因脱节 | 指出论证断点，给出适用的验证建议 |
| E07 | 同一方案有共性潜力但依赖个人环境 | 区分潜力与已推广事实，列明复用限制和接入要求 |
| E08 | 来源数据更新或人工修改课题后续接 | 恢复状态，保留修订，标记受影响结论需核验 |
| E09 | 档案有缺口，要求生成参评材料 | 草稿明确标记缺口，核心结论不把未知写成已证实 |
| E10 | 生成报告、图表和 PPT | 数字与引用一致，文件可打开，版式与渲染检查有记录 |
| E11 | 多成员摘要含旧版本、重复课题和冲突 | 按标识与版本汇总，陈旧与冲突可见，反馈可回流 |
| E12 | 在选定宿主安装并完成两种入口到汇总 | 无需依赖旧会话即可续接，依赖与未支持能力说明准确 |

定性任务由负责人按明确检查项判断；计算任务使用独立参考结果，不只用产品自己复算自己证明正确。候选发现按证据质量与可开展性评价，不把多产出候选视为更好。

建议发布条件：E01–E12 在已选支持环境中完成验证；正式材料中的无依据事实、核心数值错误和来源错配不得遗留。实际用例集、严重度口径和支持矩阵需在实施设计中固化。

## 4. Technical Specifications

本节为架构方向建议，用于约束后续设计；不视为已确定技术栈、目录规范或接口实现。

### 4.1 架构与数据流

```text
成员现有编程 Agent
        │ 按需调用 QCC Skill，指定描述 / 资料范围 / 当前课题
        ▼
资料读取与来源索引 ──→ 候选发现 / 已有改进提炼
                               │
                               ▼
                 方法规则 + 当前阶段 + 下一步建议
                               ↕
                       持续课题档案
                  事实 / 证据 / 计算 / 版本
                      │                 │
                      ▼                 ▼
               成果编译与自检       摘要导出 / 更新
         报告 / 图表 / PPT / 复用包      │
                                        ▼
                              负责人轻量汇总与反馈
                                        │
                                        └──→ 课题继续改进
```

方法规则同时供交互引导、结构校验、材料编译和评审自检使用；事实与计算结果从同一档案产生，避免多份材料分别编造或维护数字。

### 4.2 建议的数据对象

| 对象 | 核心内容 |
|---|---|
| 方法规则包 | 规则标识、版本、适用课题与阶段、输入输出、检查项、依据 |
| 候选课题 | 问题、来源、范围、价值与共性假设、未知项、拆分合并关系 |
| 课题档案 | 稳定标识、负责人、范围、规则版本、阶段状态、目标、下一步、修订信息 |
| 来源与证据 | 来源标识、定位信息、可用版本或时间、关联事实或主张、核验结果 |
| 主张与计算 | 内容、事实或估算类型、支持证据、公式与输入、结果、缺口与冲突 |
| 推广记录 | 适用条件、目标团队、复现或采用情况、成本、收益反馈及依据 |
| 交付快照 | 档案版本、使用的证据与计算、生成材料、检查结果与未解决项 |
| 课题摘要 | 课题标识与版本、三维评价摘要、阶段、关键缺口、下一步、更新时间 |

建议使用可人工检查的结构化文件维护档案与摘要，配套 Markdown 供阅读。精确格式、文件路径和迁移策略在实施设计中确定，不依赖模型记住旧会话。

### 4.3 收益核算的建议约束

以人力节省为例，建议表达为：

```text
净节省人工小时 = Σ[同类事件数 ×（基线人工处理小时 − 改善后人工处理小时）]
                 − 归属观察期的建设、运行和维护人工小时

净节省人天 = 净节省人工小时 / 约定的每人天工时
```

- 事件、周期和适用范围需可比；工时换算参数必须显式记录。
- 同一事件、团队和收益不重复计入；建设成本的一次归集或摊销方式需说明。
- 机器运行、排队、下载等耗时变化不能未经分析直接算成人力节省。
- 外推到更多使用者或更长周期属于估算场景，不能与已发生收益合并展示为实测值。
- 实际课题可采用其他适用指标；不要求所有价值都强行换算为人天。

### 4.4 集成、依赖与信息范围

- **宿主 Agent**：复用其模型、文件工具及已具备的来源访问能力；不预设所有宿主工具完全一致。
- **输入来源**：指定本地资料、仓库与工作记录为基础；Issue / PR、办公文档、表格和运行平台连接器按实际环境选定。
- **计算和材料工具**：语言、运行环境、统计与 PPT 生成库、渲染依赖待选；依赖检查应说明可执行与受限步骤。
- **负责人汇总**：标准摘要包是成员与负责人之间的交换边界；文件共享、Git、表格或其他载体由 D05 决定。
- **访问与隐私**：沿用现有来源和宿主访问范围；摘要按课题需要导出，不默认包含全部原始代码、日志和业务数据。需说明模型请求与导出包实际使用的信息范围。
- **版本**：Skill、方法规则、课题档案和交付快照需要各自可识别，历史成果能够说明所用规则与来源。

## 5. Risks & Roadmap

### 5.1 MVP 路线

以下是依赖顺序，不是时间承诺；日期、人力、预算和试点规模均待确定。

| 阶段 | 重点 | 完成依据 |
|---|---|---|
| 设计准备 | 固化三维检查规则初版、数据对象、首批宿主、输入样例、PPT 与摘要交换方案 | D01–D05 得到实施所需答案；需求与验收情境可追溯 |
| MVP 内部闭环 | 实现两种入口、课题档案、方法引导、证据、收益、推广说明、材料和轻量汇总 | US01–US10 有对应产物，E01–E12 有验证记录 |
| MVP 成员试用 | 由真实成员在自己的改进上使用，负责人审阅候选及成果 | 记录第 1.4 节指标、错误、缺口和采用反馈；不预设固定获奖数量 |
| v1.1 | 基于试点补充来源连接器、方法细则、模板及汇总体验 | 改动对应试点发现，原有链路可回归 |
| v2.0 候选方向 | 需要时增加伴随发现、自动摘要同步或更丰富的协作界面 | 根据使用反馈重新决定，非当前首期承诺 |

### 5.2 主要风险与应对

| 风险 | 影响 | 应对方向 |
|---|---|---|
| 现有资料缺基线和验证记录 | 只能证明做了工作，难以证明收益和原因 | 及早识别缺口，为后续改进提供可执行的补证任务 |
| 候选发现过度推断或追求题目数量 | 形成包装性课题，消耗成员与负责人精力 | 每个候选绑定依据与疑点，保留负责人不采纳原因 |
| 效率与人力、潜在与已实现混淆 | 收益夸大，评审无法自证 | 确定性核算、口径分离、成本与假设可追溯 |
| 推广性仅靠措辞 | 其他部门无法采用或复制收益 | 从选题共性到接入成本、复现、采用反馈逐步验证 |
| 方法规则固化了单一模板偏好 | 页面看似完整但方法不适用 | 规则有来源、版本与适用条件，允许有依据的不适用项 |
| 多宿主及本地渲染环境差异 | 安装、计算或 PPT 交付失败 | 首批支持范围明确，逐项实测并报告受限能力 |
| 读取和生成链条较长 | 延迟、模型成本或中断影响使用 | 有界读取、保存中间结果、按阶段续接，测量实际耗时与成本 |
| 摘要版本滞后或冲突 | 负责人误判进展或重复统计 | 稳定标识、修订信息、更新时间与冲突提示 |
